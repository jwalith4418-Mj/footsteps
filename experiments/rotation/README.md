# Does removing rotation make Footsteps easier to play?

Keep rotation in base-1. Printed-only placement reduced cooperative wins on the sixteen-tile paper kit. The local model could read specific orientations more reliably when it could request a tile and answer with a literal turn name. That gain did not carry over to choosing a complete tactical build. [Design question and advance criteria](https://github.com/othercriteria/footsteps/issues/54)

## What fixed orientation costs the builder

Four cooperative seats had two private tiles each, eight turns, and EXIT four east and two north. All votes approved movement and all seats passed on nominations. We paired 128 deals per policy (seeds 9400–9527), with identical initial hands, draws through the common prefix, turn budget and policy tie-breaking seed. The fixed policy could only select rotation zero, including on fallback. Divergent returns can change later draws. We repeated the panel after independently rotating each of the sixteen physical faces before each deal. These reprints preserve each tile's shape and connectivity. [Deals and outcomes](cooperative/deals.csv)

| Kit and scripted policy | Wins allowing rotation | Wins fixed | Won only with rotation | Won only fixed |
|---|---:|---:|---:|---:|
| Printed, prefer onward exits | 125/128 | 84/128 | 42 | 1 |
| Printed, search reachable floor | 123/128 | 79/128 | 45 | 1 |
| Reprinted, prefer onward exits | 124/128 | 35/128 | 89 | 0 |
| Reprinted, search reachable floor | 118/128 | 36/128 | 84 | 2 |

On the printed kit every opening hand in the sample offered a productive fixed build. The shortage appeared after the opening. For the onward-exit policy, when there was no existing step closer to EXIT, the builder lacked a productive build on 207/767 turns with fixed orientation and 16/649 with rotation. Here “productive” means an enterable new tile closer to EXIT with a usable outgoing side toward EXIT. This is a local test. A detour or remote build can still help. The deal CSV includes the first such missed opportunity and the number of these turns where rotation would unlock a productive alternative in the actual hand. A suspicious-looking build can have different evidentiary value under the two rules.

For example, the route policy started deal 9400 holding 74, 188, 121 and 16 after drawing. With rotation it built 74 north of START and reached EXIT on turn seven. Playing printed-only, it built 188 east of START, went around the east side and ran out of turns at (5, 1). These are two histories generated by the same policy. Neither is a proof of optimal play. The records contain ordinary base-1 commands. [Rotating replay](cooperative/9400-route-rotate.json) · [Printed-only replay](cooperative/9400-route-fixed.json)

## What assistance buys on the same model decisions

We used local `qwen3.5:9b-q8_0` (ID `a8ee95bc3592`), temperature zero, seed one, 4096 context, thinking off and a 30-second decision budget. For the reading test, the only face was a straight directed tile (40) or an elbow (33). Each of the four requested entrance/exit pairs had one correct clockwise orientation per face. The square was supplied. Each question was repeated with its legal menus reversed. The resulting 16 decisions cover eight distinct requests.

The automatic table showed the four rows for each distinct held face. The optional native tool returned the same four rows for one requested face. The numeric interface took an index into the offered rotations. The named interface accepted literals such as `turn_1` for clockwise 90° regardless of menu order. In the printed-only arm the model chose just face and square, and rotation was fixed to zero.

| Interface | Correct readings, rotation index | Correct readings, named turn | Successful full builds, index / named |
|---|---:|---:|---:|
| Unaided | 5/16 | 5/16 | 0/12 · 0/12 |
| Automatic table | 5/16 | 7/16 | 0/12 · 0/12 |
| Optional lookup | 6/16 | 11/16 | 0/12 · 0/12 |
| Printed-only | 4/16 feasible and achieved | — | 0/12 · — |

For the optional lookup, changing menu order took index answers from 6/8 to 0/8. The named interface scored 5/8 in ordinary order and 6/8 in reverse. In the printed-only arm all four feasible readings required the only available orientation. [Choices with indices and printed-only control](decisions.csv) · [Choices with named turns](named.csv)

The social cases restored Blue’s last viable build on 8602, the Red guest’s trap, and the 8101/8102 three-seat builds with Blue or Red in the acting seat. Each was presented in both menu orders. We enumerated all legal actions in each menu before interpreting the score. Blue needed to enable a step with an optimistic route to EXIT in time. Red needed to seal the marker permanently. All twelve decisions had a successful printed-only option. On 8602 fixed orientation reduced the legal combinations from 160 to 40 and the successful ones from four to one. On the Red guest floor it reduced 128 to 32 and eight to one. For the Blue decision the successful share stayed at 1/40 under either rule. For the guest decision the share fell from 1/16 to 1/32.

**On the twelve named-lookup social choices, an ideal rotation of the chosen face at the chosen square could rescue just one.** In the other eleven even substituting any face from the builder's hand could not make that square accomplish the tactic. The model asked for a face with a viable build somewhere on all twelve and then placed a different face on all twelve. That behavior is observable. We cannot tell from the request alone whether it rejected the face on purpose or lost track of it when constructing the indexed action. The paired board states and alignments share geometry, so these small denominators should not be treated as independent games.

## What a lookup tells us

Every lookup opportunity produced a valid request on this frozen panel. In a separate control we offered the same tool when the only held face was 0 (all ports closed) or 255 (all ports open). Qwen asked on **8/8**, including **4/4** when explicitly told all rotations had identical entrances and exits. Request frequency under this offer tells us little about the model's uncertainty. Which face it asks about, how that relates to its eventual build, and its accuracy with and without the returned information are more discriminating. [Invariant tile controls](invariant.csv)

The former 96-token tool-selection prompt cut one diagnostic run off before a native call appeared. With the same position and a 512-token limit it returned a native request after 325 generated tokens. The present tool-selection prompt asks directly for one call or an explicit `{}`, with a 384-token ceiling and at most half of the original time. The client distinguishes explicit skips, truncation, unavailable service, malformed calls and completed lookups. With both tools enabled it may also choose the existing placement preview. The frozen panel offered the rotation lookup alone.

On the twelve named-turn social choices, median reported prompt tokens were 783 unaided, 975 with automatic tables and 1,741 across both requests with optional lookup. Median elapsed times were 0.70, 0.64 and 2.90 seconds respectively. These are descriptive workstation measurements. The GPU was shared for part of the runs. All 196 frozen decisions produced an accepted reply. A full table has other seats, public discussion, guided builds and private explanations, all of which can affect these numbers.

## One lookup that changed the whole floor

On the matched five-seat 8602 deal, all eight builders requested a lookup and all eight submitted a placement in time. Only Blue P2 on turn three actually placed the inspected face. Red won by depletion on turn eight. The floor already guaranteed that result five turns earlier. [Lookup receipts](receipts.csv) · [Full record](social/8602-red1+3.json) · [Ordinary comparison](../exit-origin/social/8602-red1+3.json)

Immediately before **event 22**, the marker was on face 47 at (−1, −2). Its only exit points east to the unbuilt square (0, −2). P2 looked up face 82 and put it on exactly that square. With two clockwise quarter turns its entrance would face west and its exits would face north and south. The marker could step onto it, with a three-step route from its original square under optimistic future tiles. P2 chose three turns instead. That gives a north entrance and east/west exits. The facing edge was closed and the referee certifies permanent confinement. The recorded reason even named a different destination from the actual submitted action. This is a case where correcting rotation alone at the chosen face and square would have preserved a chance.

The 3 Blue / 2 Red table had the same kit, seating, budget and assistance on social decisions as the ordinary control. It used private notes and worked forward-build examples, while the frozen probe had neither. Its single outcome provides a worked failure. For a next comparison, let the model identify the proposed face and square by literal values, then read the candidate edge and decide to keep or revise the build before committing. Test event 22 alongside a deliberate Red block and a useful remote build. [Tactical transfer issue](https://github.com/othercriteria/footsteps/issues/76)

## Reproduce

Use fresh output paths from the repository root. The cooperative simulation and evidence summaries run without Ollama. For comparable timing, run model jobs sequentially.

```sh
work=$(mktemp -d)
python -m experiments.rotation_deals "$work/cooperative"
python -m experiments.rotation_probe "$work/decisions.csv"
python -m experiments.rotation_probe "$work/named.csv" --named-rotations
python -m experiments.rotation_probe "$work/invariant.csv" --controls
python -m experiments.rotation_summary "$work"
python -m experiments.social_evidence --roles BRBRB --paired-fifth-hand \
  --arm receipt --debate --model-floor --outcome-policy --kit-counts 29 29 \
  --kit-seed 8700 --seeds 8602 --goal 2 2 --action-brief --exit-origin \
  --rotation-aid tool --named-rotations --out "$work/social" --private-notes "$work/private"
python -m experiments.rotation_summary "$work" --social-notes "$work/private/8602-red1+3.jsonl" > "$work/receipts.csv"
python -m footsteps view "$work/social/8602-red1+3.json" --omniscient \
  --notes "$work/private/8602-red1+3.jsonl" -o "$work/8602.html"
```

The base rules and record format retain all four rotations. Printed-only is an experimental restriction on the choices offered. Human handling time, the credibility of a constrained builder’s explanation, and whether redesigning the kit would improve a fixed-orientation game remain open.
